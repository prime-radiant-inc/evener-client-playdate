# Physical SDK TCP investigation, 2026-10-12

## Scope and environment

The [standalone probe](../../check/sdk-tcp/README.md) isolates physical TCP
reception without the Evener socket adapter or any application protocol. The
results below concern a receive stall. They do not yet prove the same root cause
for Evener's separately observed pending-write timeout or malformed DERP frame.

- Physical Playdate firmware `1a63be33-3.1.2-release.213590`, SDK 3.1.2.
- ARM GNU 15.3.1; hardware and macOS simulator targets compile.
- Plain TCP on the local Wi-Fi network; no TLS, tailnet, microphone or credentials.
- 30 Hz update, 64 KiB SDK receive buffer, fixed synthetic input and receipts.
- Radio version queried read-only with `AT+GMR`: ESP-AT
  `2.0.0.0-dev(b6850a4 - Oct 24 2019 12:10:13)`, SDK
  `v3.3-beta3-170-g91f29bef17-dirt`, Panic build
  `021d78c`, compiled April 6, 2026.

## Results

| Physical run | Verified device receive | Server received | Outcome |
| --- | ---: | ---: | --- |
| Direct SDK duplex | 15,920 bytes | 1,170 bytes / 10 receipts | Reception stalled, SDK error and pending count stayed zero |
| Direct SDK download-only | 1,048,576 bytes | 117 bytes / 1 receipt | Both ends passed; server completed in 5.283 seconds |
| Duplex with SDK worker callback after each write | 19,064 bytes | 1,170 bytes / 10 receipts | Reception stalled, then closure after 30.525 seconds without read progress |
| Duplex, server writes paced at 2,400 bytes per 33 ms | 19,200 bytes | 1,170 bytes / 10 receipts | Reception stalled, then closure after 30.426 seconds without read progress |
| Repeat download-only, address selected through launch arguments | 1,048,576 bytes | 117 bytes / 1 receipt | Both ends passed; server completed in 4.815 seconds |
| Repeat direct SDK duplex, same launchable build | 2,920 bytes | 1,170 bytes / 10 receipts | Reception stalled, then closure after 30.624 seconds without read progress |
| Separate plain TCP receive/send sockets | 1,048,576 bytes | 1,170 bytes / 10 receipts | Both ends passed; server completed in 4.822 seconds |
| Duplex followed by automatic app restart | 8,120 bytes before restart; 1,048,576 after | 10 receipts before restart; 1 after | Restart after five seconds of receive inactivity restored the download; control completed in 4.891 seconds |
| Blocked outgoing write followed by automatic app restart | 1,048,576 bytes after restart | 117 bytes / 1 control receipt | Restart while 4096 bytes and a worker callback remained pending restored the download; control completed in 4.872 seconds |

The server observed a zero peer receive window in the stalled runs. Outgoing
receipts reached the server correctly. The failing byte counts differ, so these
runs do not establish a fixed receive-size limit. A zero SDK pending count and
a completed worker callback are both insufficient to prevent this receive stall.
Removing the client adapter does not remove the failure.

## App restart and connection budget

The split-socket result isolates one successful synthetic topology. It does not
qualify a production two-relay design. Playdate permits only two simultaneous
SDK TLS connections; Evener reserves one for DERP and one for direct OpenAI
transcription. Control maintenance takes exclusive access between these uses.

The SDK's `system.restartGame` reinitializes the runtime and passes launch
arguments to the next instance. In both restart experiments the app itself
requested that restart; the USB driver did not relaunch it between phases.
The blocked-write run had accepted 49,152 bytes before stalling with 4096 bytes
pending. Its queued worker callback had not arrived when it requested restart.
The host left that first connection open and unread until the replacement
connection completed. Recovery therefore did not depend on the host relieving
backpressure or closing the old socket. The device then verified every byte of
the MiB control, and the host verified the exact receipt and EOF.

These are plain TCP recovery qualifications, not proof that restarting prevents
the underlying duplex failure or that TLS/DERP and transcription work end to end.

## Radio investigation

An [Espressif issue](https://github.com/espressif/esp-at/issues/302) reports lost
receive notifications when incoming data overlaps an outgoing AT send. The
upstream repair in `ec7a3f2b1200d410722f037a54ae54f6e4df259f` updates the
binary AT core and describes notifying the socket monitor after sending data
status; `7f9307b6a22e2cd7fe944d957267e0000c0d51f7` follows with a change to
printing received data while connected. This is a relevant lead, not proof that
Panic's radio build lacks those fixes. Its version base predates the upstream
repair, but its later private build may contain backports.

The device's current USB help lists `espfile` and `espflash`. This establishes an
existing console update mechanism, not a supported app-callable updater or a
verified replacement image. No flashing, unlock, radio configuration change or
firmware replacement was performed. A compatible image, its effect on ordinary
system networking, and a verified recovery path remain prerequisites to a radio
firmware experiment. A subsequent ordinary `espreset` returned success but did
not recover the blocked SDK worker during 35 seconds of observation. Resetting
the radio alone therefore did not restore the running client's connection.

## Client qualification

The 2,400-byte inner TCP receive-window experiment is distinct from server-rate
pacing. It restricts the Hub's unacknowledged tunneled data. It has loaded the
reported group conversation and loaded it again after native control maintenance.
A later maintenance cycle retired the relay while 495 SDK write bytes remained
pending. The worker did not reach the completion fence, so further connections
could not be admitted. The dedicated verification draft stayed saved in review;
the send attempt did not reach the Hub. The Hub's before/after thread reads
remained at six turns and 63,146 serialized bytes. This experiment therefore
failed end-to-end qualification and was reverted. No client networking fix is
established by these runs.

## Runtime recovery integration

An initial client fallback loaded the reported group conversation, encountered
117 pending DERP bytes and the SDK write-progress timeout, then restarted itself
and successfully read the same conversation again. In a separate run, the saved
verification draft reached `turn/start` and its expected reply was observed on
the Hub. A subsequent 13-byte DERP write stall triggered another restart; the
runtime restored its view twice and then faulted in the firmware allocator one
second after restarting. That build therefore did not qualify as a reliable
recovery implementation despite the successful delivery. Plain TCP restart
success alone is insufficient evidence for the TLS client lifecycle.

The failing trace contains one application restart request and two runtime
terminations, the second only 0.46 seconds after restoration. The fault occurred
in `dlmalloc_usable_size` in firmware; this identifies where an invalid pointer
surfaced, not its origin. Ordinary termination repeated socket cleanup after the
restart request. Even closing an already cleared WebSocket can call the global
socket tick, which can queue or retire SDK work. That interaction is a concrete
candidate for investigation, not an established cause of the allocator fault.

The revised candidate flushes and closes audio files without explicit socket
teardown, and suppresses update, permission, menu and lifecycle callbacks once
restart is requested. It also checkpoints the transcript incarnation and
protects the currently visible message when a full older window merges with the
latest page. A fresh read still owns send authorization and mutation replay.
Both ARM and Simulator targets compile. Focused socket, storage and Hub recovery
checks pass normally and under AddressSanitizer/UndefinedBehaviorSanitizer,
including two-TLS admission, failed checkpoint flush, same/changed incarnation
and a full 64-message older window. These checks do not execute firmware teardown.

The revised lifecycle was subsequently installed and exercised in the
[next physical run](2026-10-13-runtime-recovery.md). That run recovered one natural
DERP stall and completed two physical dictations and sends, including transcription
alongside the established relay. Repeated stalled-worker recovery and the final
crash-log check remain open; no general firmware repair is established.

## Device restoration

The original installed Evener bundle was restored after the window experiment.
Hash comparisons confirmed that installation and removal preserved the existing
Evener pairing, drafts and caches. No older saved-data backup was copied back
onto the device.

The later runtime-recovery experiments installed the initial fallback build;
that is the last installed Evener executable, and it exhibited the allocator
fault described above. The revised candidate and return to the normal Evener
app could not be completed after USB disappeared. Diagnostic app bundles remain
on the device. The latest pairing and saved data have a private backup, and the
original executable is retained separately for recovery. No private bundles,
data backups or raw diagnostic captures belong in this repository.
